# Customers, API keys and usage

This phase adds PostgreSQL customer storage, hashed API keys, immediate revocation, durable usage metadata, a fixed UTC minute limit and calendar-month quota per customer. Limits are shared across all keys, routes and server processes. No money is charged.

## Activate against your database

Use PostgreSQL 17+ and a dedicated database. Have its administrator create the database and a role for Rafid; do not use a PostgreSQL superuser in the app. Keep credentials in `.env` or your secret manager. This implementation does not change an existing PostgreSQL service or discover its passwords.

In `C:\Projects\rafid-agent-api\.env`, configure:

```dotenv
AUTH_MODE=postgres
DATABASE_URL=postgresql://rafid:YOUR_URL_ENCODED_PASSWORD@127.0.0.1:5432/rafid
```

The URL above is a template, not a working credential. For remote production databases configure verified TLS, e.g. an appropriate `sslmode=verify-full` connection and trusted certificate. Do not disable certificate verification.

From PowerShell:

```powershell
Set-Location 'C:\Projects\rafid-agent-api'
npm.cmd run admin -- migrate
npm.cmd run admin -- customer:create 'Customer One' 60 10000
```

The last two numbers are requests per minute and requests per UTC calendar month. Copy the returned customer `id` into the next command:

```powershell
npm.cmd run admin -- key:issue '<customer-id>' 'primary'
```

The new API key is printed **once**. Save it privately and use it in `X-API-Key`. The database stores only its SHA-256 digest and a random key ID; it cannot recover the original key. Do not paste the key into support messages or logs. New keys contain 256 bits of randomness; fast hashing is appropriate for random secrets, unlike human passwords.

Stop the current development server with Ctrl+C and restart it:

```powershell
npm.cmd run dev
```

In postgres mode, `RAFID_API_KEYS` and `API_KEY` are ignored, with no fallback on database failure. Migration is explicit; startup checks that migration 1 exists. Existing local env-key mode remains available for development; production (`NODE_ENV=production`) requires postgres mode. Your existing `.env` is not automatically modified by this change.

## Administration

Commands run locally with database credentials; no unauthenticated admin HTTP routes are added. Treat database/CLI access as privileged operator access.

```powershell
npm.cmd run admin -- usage '<customer-id>'
npm.cmd run admin -- key:revoke '<customer-id>' '<key-id>'
npm.cmd run admin -- customer:disable '<customer-id>'
npm.cmd run admin -- customer:enable '<customer-id>'
```

For rotation, issue a new key, update the client, then revoke the old key. Revocation requires the matching customer ID. Requests admitted before revocation may finish; subsequent admission checks reject the key. Disabling a customer blocks all its keys. Usage returns only the latest 100 entries for the specified customer. There is no customer-facing self-service endpoint in this phase.

## Counting and failure semantics

- Only authenticated REST business routes are metered. Canonical and legacy paths use the same customer counters. Public discovery/liveness and local MCP stdio are not metered.
- Every admitted request consumes one monthly unit and one minute unit, including invalid JSON, invalid inputs and downstream failures. Units are not money; there are no automatic refunds.
- Limit checks and reservation run in one transaction under a customer row lock. Simultaneous requests across processes cannot overspend the configured quota. The database computes UTC boundaries after acquiring the lock; windows reset lazily on the next request.
- Minute limits are fixed windows, not sliding windows: traffic can burst on either side of the boundary. Monthly quota resets at 00:00 UTC on the first day of each month.
- Rejected limits return 429 with `RATE_LIMITED` or `QUOTA_EXCEEDED`, record a rejected usage entry and do not consume quota. Invalid/revoked keys return 401 and have no customer usage entry.
- Usage contains customer/key IDs, request ID, tool name, timestamps, admitted flag, final status and duration. It contains no property inputs, API key, body, headers or query strings.
- Final usage status is written before the HTTP response. Storage failure returns sanitized 503 and never bypasses limits. A process crash/disconnect can leave a pending reservation with null status/duration; quota stays consumed. Completion is idempotent. Duration measures server processing through calculation/error handling, not socket delivery time.
- The ledger records execution status, not proof of payment or delivery. Request IDs are generated by the server; a retried client call is a new metered request. Payment idempotency/reconciliation remains separate future work.

The runtime DB role needs SELECT/INSERT/UPDATE on customer/key/counter/usage tables and SELECT on migrations. Use a separate migration/operator role for schema changes and key administration in production. Application tenant scoping is tested; PostgreSQL row-level security and a customer login/dashboard are not implemented. Unknown-key traffic still needs an edge/global rate limiter. Define retention/archiving for usage records before production growth.

## Tests

Use a **dedicated test database**, because these tests migrate tables and insert customer/key/usage fixtures. They do not delete existing rows.

```powershell
$env:TEST_DATABASE_URL = '<connection-url-for-test-database>'
npm.cmd run test:db
npm.cmd run typecheck
npm.cmd test
```

`test:db` fails if the URL is absent. Regular `npm test` skips the database integration group when TEST_DATABASE_URL is absent. Tests cover separate PostgreSQL pools, concurrent shared quotas, UTC rollover, tenant-scoped revocation/usage, disabled customers, persisted digests, HTTP final statuses, privacy and storage failure.

Verified on an isolated PostgreSQL 18 cluster: all 40 tests passed with no skips, plus production build and typecheck. The verification cluster is not your application database.

Transaction implementation follows the [node-postgres single-client transaction guidance](https://node-postgres.com/features/transactions) and [PostgreSQL row locking semantics](https://www.postgresql.org/docs/17/explicit-locking.html).
