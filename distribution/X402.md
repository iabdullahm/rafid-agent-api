# x402 Guide

Rafid's x402 route family (`POST /api/v1/x402/<capability-path>`) lets an agent pay per call, on-chain, with no account, no API key, and no sign-up. This document describes the protocol as implemented (`src/billing/x402.ts`, `src/config/env.ts`) — for anything deployment-specific (is x402 enabled right now, which network, which facilitator), always read it live from `GET /api/v1/x402` or `GET /api/v1/x402/status` rather than trusting a cached copy of this page, including this one.

## The pay-per-call model

Each capability has one price, in USD, read from a single catalog (`src/billing/catalog.ts`, itself derived from `src/domain/capabilities.ts` — never a second literal):

| Capability | Price |
|---|---|
| `analyze_property` | $0.01 |
| `compare_properties` | $0.03 |
| `estimate_maintenance` | $0.02 |
| `analyze_oman_property` | $0.25 |

The same price is what `BillingService`, the x402 payment gate, `GET /api/v1/pricing`, `GET /api/v1/tools`, `GET /api/v1/capabilities`, `GET /api/v1/x402` and the OpenAPI `402` response description all read — there is no separate x402-specific price list to fall out of sync.

## Payment flow

1. **Discover the price and terms.** `GET /api/v1/x402` is always reachable, independent of whether x402 is currently enabled, and lists every tool's x402 endpoint and price, plus the current network/facilitator/`payTo` address when enabled. `GET /api/v1/x402/status` gives the smaller, always-safe factual status shown above.
2. **Call unpaid, once.** `POST` the x402 endpoint with your normal JSON body and no `X-PAYMENT` header.
3. **Receive `402 Payment Required`.** The response carries a `PAYMENT-REQUIRED` header: a base64-encoded JSON object per the x402 protocol (v2) describing `accepts` — the accepted payment scheme (`"exact"`), price, network, asset, and receiving address. **The payment terms are in this header, not the JSON body** (the body is intentionally `{}`) — an x402-naive HTTP client that only looks at the body will miss them.
4. **Satisfy payment.** Construct a valid payment proof for the `exact` scheme on the stated network/asset, per the x402 protocol specification (out of scope for this document — see the x402 protocol's own spec, or use an x402-aware client library that does this for you).
5. **Retry with `X-PAYMENT`.** Send the same request again with an `X-PAYMENT` header carrying the payment proof. If it verifies and settles, you get the normal `200` response — the same envelope and schema as the API-key route for the same capability.
6. **Settlement** happens on-chain, via the configured facilitator (Coinbase Developer Platform, or the x402 public facilitator on networks it supports). Rafid does not hold funds or run its own settlement layer — the facilitator verifies and settles the payment, and Rafid's gate only checks that a valid, sufficient payment was presented before letting the request through to `execute()`.

## Bazaar discovery metadata

Every x402 route (`src/billing/x402.ts`) declares [x402 Bazaar](https://docs.x402.org/extensions/bazaar) discovery metadata via `@x402/extensions/bazaar`'s `declareDiscoveryExtension()` — the same input/output JSON Schema and hand-verified example already published via OpenAPI (`z.toJSONSchema(c.input)`/`(c.output)`, `c.example`/`c.exampleOutput` from `src/domain/capabilities.ts`), so a Bazaar-aware client or facilitator can read a route's expected request/response shape from the `402` response itself (`extensions.bazaar`) without a separate manual listing.

**This declaration does not by itself register Rafid in any Bazaar catalog.** Per the Bazaar spec, cataloging happens only when a facilitator processes a real, settled `PaymentPayload` that echoes this declaration back — payment settlement, not declaration, is what triggers indexing, and whether/how a resource then actually appears is stated by the spec itself to be "an implementation detail of the facilitator operator," not guaranteed by settlement alone. As of this writing there is also an open, unresolved report ([x402-foundation/x402#2112](https://github.com/x402-foundation/x402/issues/2112)) of services with genuine, repeated settled payments through the Coinbase Developer Platform facilitator — the facilitator this production deployment uses — never appearing in the Bazaar catalog, with a maintainer-unconfirmed theory that indexing may require the receiving wallet to be under a registered CDP developer account. So: the discovery metadata above is real and correctly wired, but a real settled payment is a separate, deliberate step or on-chain transaction — never taken automatically by this codebase or by Claude on a user's behalf — and even then Bazaar cataloging isn't guaranteed today.

## Unpaid curl example

```bash
curl -s -i -X POST https://api.rafidsystem.com/api/v1/x402/property/analyze \
  -H "Content-Type: application/json" \
  -d '{"propertyValue":85000,"annualRent":7200}'
```

Expect `HTTP/1.1 402 Payment Required` with a `PAYMENT-REQUIRED` response header. Decode it (`base64 -d`, or your language's base64 decoder) to see the accepted payment options as JSON.

## x402 client example (safe pseudocode)

```javascript
// Illustrative — use a real x402-aware HTTP client library for actual payment
// construction/signing; this sketch shows the request/response shape only, and
// never touches a private key or wallet secret directly.
async function callWithX402(url, body, wallet) {
  const first = await fetch(url, { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify(body) });
  if (first.status !== 402) return first.json(); // already paid for, or free

  const requirements = JSON.parse(atob(first.headers.get("PAYMENT-REQUIRED")));
  // `wallet` is an x402-aware payment signer supplied by your own client library —
  // never construct or transmit a raw private key by hand.
  const paymentHeader = await wallet.buildPayment(requirements.accepts[0]);

  const second = await fetch(url, {
    method: "POST",
    headers: { "Content-Type": "application/json", "X-PAYMENT": paymentHeader },
    body: JSON.stringify(body)
  });
  return second.json();
}
```

## Payment retry

A `402` is not an error to give up on — it's the protocol's normal first step. Retry exactly once with a valid `X-PAYMENT` header after satisfying the stated requirements. If the retry still fails, read the response body's `error.code`/`error.message` — the same structured error envelope every route uses (`400 INVALID_INPUT`, `413 PAYLOAD_TOO_LARGE`, `415 UNSUPPORTED_MEDIA_TYPE`, `429 RATE_LIMITED`, `500 INTERNAL_ERROR`, `503 SERVICE_UNAVAILABLE`) — before retrying blindly again.

## Security warnings

- **Never send a wallet private key to Rafid, or put one in a request.** x402 payment proofs are constructed client-side by your own wallet/signer; Rafid's server never asks for, receives, or needs your private key.
- **Rafid's own receiving wallet's private key, the CDP facilitator API secret, and any other server-side x402 credential are never exposed by any endpoint in this API** — `GET /api/v1/x402`, `GET /api/v1/x402/status`, `/agent.json` and `/openapi.json` all expose only the public, receive-side `payTo` address and non-secret configuration flags (`enabled`, `mode`, `network`, `asset`, `facilitator`, `walletConfigured: boolean`, `paymentEnforcement: boolean`) — never a key value. See [`SECURITY.md`](SECURITY.md).
- **A `walletConfigured: true` or `paymentEnforcement: true` flag is a boolean status, not proof of anything about the underlying key material** — it only says a wallet address is configured and payment is being enforced.
- **This document deliberately does not print the live `payTo` wallet address**, even though it's not secret, to avoid this file going stale the next time it changes — read it live from `GET /api/v1/x402` or `GET /agent.json`.
